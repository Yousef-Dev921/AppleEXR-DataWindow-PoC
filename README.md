# libAppleEXR dataWindow memory exhaustion — PoC and write-up

A reproducible memory-exhaustion defect in `libAppleEXR.dylib`
(reached through `ImageIO.framework`) on **macOS 26.5 (build 25F71)**
running on Apple Silicon. A **384-byte** OpenEXR file drives the
decoder to commit about **1.85 GiB** of resident physical memory, and
hangs the Quick Look thumbnailer.

Reported to Apple Product Security and closed without being
classified as an exploitable vulnerability. Published here for the
record. **No memory corruption or code execution is claimed.** The
behaviour is a denial-of-service class issue: sustained resident
commit, plus a Quick Look hang.

## Repository layout

```
pocs/         exr.exr (the PoC) + SHA-256 checksum.
reproduce/    vm_probe.m (source only; verify.sh rebuilds it),
              verify.sh (one-shot reproduction),
              ql_wrap.sh (qlmanage with a timeout).
evidence/     measurements.txt — captured run of verify.sh.
              preview-app/ — Preview.app sampling notes.
              nsimage/ — AppKit per-step reproducer; isolates
              NSBitmapImageRep impact.
              ios/ — iPhone test log (device IDs redacted).
analysis/     exr-datawindow.md — full write-up, and a
              supplementary x86_64 disassembly excerpt.
```

## Quick verify

```
cd AppleEXR-DataWindow-PoC
./reproduce/verify.sh > evidence.txt 2>&1
```

The script:
- re-execs itself under `arch -arm64` if invoked from a Rosetta shell;
- rebuilds `vm_probe` from source on each run;
- prints the binary architectures it uses;
- captures `task_info(TASK_VM_INFO)`, `/usr/bin/time -l`, and
  `qlmanage` measurements against the PoC and a legitimate EXR
  control file (from Xcode, if installed);
- bounds each `qlmanage` invocation to a 20-second budget (the
  PoC hangs `qlmanage` indefinitely).

Preview.app and iOS observations are not regenerated by
`verify.sh`; they are captured separately under
`evidence/preview-app/` and `evidence/ios/`.

## Headline numbers (from `evidence/measurements.txt`)

```
EXR PoC (384 B)
  task_info resident delta:  Run 1 = 1.69 GiB; Runs 2–3 = 1.85 GiB
  /usr/bin/time -l peak:     ~1.85 GiB on the captured fresh-process run
  NSBitmapImageRep initWithData:  +1.52 GiB  (evidence/nsimage/)
  qlmanage:                  hangs for 20 s with no progress, killed.
                             qlmanage process never reached the memory-
                             commit path in this run.
  Preview.app:               stable at ~72 MiB (not affected)

Legitimate EXR control (Xcode's twinkle.exr, 246,981 bytes)
  task_info resident delta:  4.94 MiB
  /usr/bin/time -l peak:     6.35 MiB
  qlmanage peak footprint:   67 MiB    (thumbnail produced in 1 s)
```

A legitimate EXR file about 640× larger than the PoC uses roughly
300× (`/usr/bin/time`) to 380× (`task_info`) less memory through the
same APIs. The behaviour is specific to the malformed `dataWindow`
field described in [analysis/exr-datawindow.md](analysis/exr-datawindow.md),
not a general framework characteristic.

## The finding in one paragraph

In `DecompressedLocations::CreateDecompressedLocations` (link-time
`0x7ffa15917b34` in the x86_64 slice), the allocation size is
computed as `arg2 * (arg3 >> 29 & ~7) + arg2 * 8 + 24`. The PoC's
`dataWindow` `box2i` contains `yMin = 0x89ffd8ff` (signed int32 =
−1,979,721,473), making the derived height 1,979,721,474 pixels at
512 px width. The `jo` / `jb` overflow guards after the `mul`/`add`
handle full `size_t` overflow, but no earlier bound exists on the
attacker-controlled image extents. Reproduces in `CGImageSource` and
`NSBitmapImageRep initWithData:`. Full write-up in
[analysis/exr-datawindow.md](analysis/exr-datawindow.md); disassembly
excerpt in [analysis/exr-disassembly.txt](analysis/exr-disassembly.txt).

## Measurement environment

- macOS 26.5 Tahoe, build 25F71
- Mac15,12 with Apple M3, 16 GiB RAM
- Measurement tool compiled `-arch arm64`; `sysctl.proc_translated = 0`
  confirms native arm64 execution at runtime

## iOS

A signed test app on an iPhone 15 Plus running iOS 26.5 reproduces
the virtual reservation (~1.85 GiB of virtual growth, matching macOS),
but iOS does not commit the pages in this code path — resident growth
is only +720 KiB. iOS is **not** characterised here as affected as a
user-visible DoS. The log is in `evidence/ios/` for completeness.

## Disclosure

- Reported to Apple Product Security.
- Apple closed the report without classifying the behaviour as an
  exploitable vulnerability.
- Published here to document the finding. The PoC file is malformed
  but inert — a header-only test case that exercises decoder
  size-handling, not a dropper, exploit, or payload.
