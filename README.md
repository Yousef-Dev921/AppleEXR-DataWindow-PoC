# libAppleEXR dataWindow memory exhaustion — PoC and write-up

A reproducible memory-exhaustion defect in `libAppleEXR.dylib`
(reached through `ImageIO.framework`) on **macOS 26.5 (build 25F71)**
running on Apple Silicon. A **384-byte** OpenEXR file drives the
decoder to commit about **1.85 GiB** of resident physical memory.
This still reproduces on macOS 27.0.1 (build 26A434).

Reported to Apple Product Security and closed without being
classified as an exploitable vulnerability. Published here for the
record. **No memory corruption or code execution is claimed.**

## Status on macOS 27.0.1

Re-tested on 2026-10-19 on **macOS 27.0.1 (build 26A434)**, Mac17,3
with Apple M5, 16 GiB RAM, using the same `verify.sh`
(`evidence/macos-27.0.1/`). **The behaviour still reproduces:**

```
EXR PoC (384 B)
  task_info resident delta:  Run 1 = 1.25 GiB; Run 2 = 1.66 GiB; Run 3 = 1.85 GiB
  /usr/bin/time -l peak:     1.85 GiB
  NSBitmapImageRep initWithData:  +1.70 GiB
  qlmanage:                  hangs, no thumbnail, killed after 20 s
                             (qlmanage peak footprint 8.3 MiB)

Legitimate EXR control (Xcode's twinkle.exr)
  task_info resident delta:  5.20 MiB
  /usr/bin/time -l peak:     14.7 MiB
  qlmanage peak footprint:   59.3 MiB  (thumbnail produced in 1 s)
```

The per-run `task_info` delta varies more than on 26.5. An earlier
run the same day (`evidence/macos-27.0.1/measurements-earlier-run.txt`)
measured 1.13, 1.55 and 1.76 GiB. The fresh-process `/usr/bin/time`
peak was 1.85 GiB both times.

**Quick Look on 27.0.1.** `qlmanage` still hangs on the PoC, but it
also hangs on unrelated broken files: an 8-byte EXR header and an
invalid PNG (`evidence/macos-27.0.1/quicklook-check.txt`). On 27.0.1
the hang is therefore not evidence of this defect. The memory commit
through `CGImageSource` and `NSBitmapImageRep` is the finding.

Preview.app and iOS were not re-tested on the new releases.

## What this is, and what it is not

- **What it is:** a resource-exhaustion robustness bug. The decoder
  takes image dimensions from the file and sizes an internal table
  from them, without first checking that they are plausible for a
  384-byte file. One small file makes the decoding process hold about
  1.85 GiB of physical memory.
- **What it is not:** no crash, out-of-bounds access, memory
  corruption, or code execution was observed or is claimed. In every
  run the allocation succeeded and the process continued normally.
- **Scope:** the cost falls on the process that decodes the file.
  Through the APIs measured here (`CGImageSource` with caching and
  thumbnail options, `NSBitmapImageRep initWithData:`), that is about
  1.85 GiB per decode. Preview.app on 26.5 was not affected (~72 MiB).
  Which other applications use these APIs on EXR input was not
  surveyed.
- **Apple's assessment:** Apple reviewed the report and did not
  classify it as a security vulnerability. This repository does not
  dispute that. It documents a reproducible bug with the evidence
  needed to check it.

The sections below document the original measurements on macOS 26.5.

## Quick verify

```
cd AppleEXR-DataWindow-PoC
./reproduce/verify.sh > evidence.txt 2>&1
```

The script:
- re-execs itself under `arch -arm64` if invoked from a Rosetta shell;
- rebuilds `vm_probe` from source on each run;
- prints the binary architectures it uses;
- captures `task_info(TASK_VM_INFO)`, `/usr/bin/time -l`, and
  `qlmanage` measurements against the PoC and a legitimate EXR
  control file (from Xcode, if installed);
- bounds each `qlmanage` invocation to a 20-second budget and kills
  `qlmanage` if it has not finished (it does not finish on the PoC).

Preview.app and iOS observations are not regenerated by
`verify.sh`; they are captured separately under
`evidence/preview-app/` and `evidence/ios/`.

## Headline numbers on macOS 26.5 (from `evidence/`)

```
EXR PoC (384 B)
  task_info resident delta:  Run 1 = 1.69 GiB; Runs 2–3 = 1.85 GiB
  /usr/bin/time -l peak:     ~1.85 GiB on the captured fresh-process run
  NSBitmapImageRep initWithData:  +1.52 GiB  (evidence/nsimage/)
  qlmanage:                  did not finish within 20 s, no thumbnail;
                             no memory commit was observed in the
                             qlmanage process itself.
  Preview.app:               stable at ~72 MiB (not affected)

Legitimate EXR control (Xcode's twinkle.exr, 246,981 bytes)
  task_info resident delta:  4.94 MiB
  /usr/bin/time -l peak:     6.35 MiB
  qlmanage peak footprint:   67 MiB    (thumbnail produced in 1 s)
```

A legitimate EXR file about 640× larger than the PoC uses roughly
300× (`/usr/bin/time`) to 380× (`task_info`) less memory through the
same APIs. The behaviour is specific to the malformed `dataWindow`
field described in [analysis/exr-datawindow.md](analysis/exr-datawindow.md),
not a general framework characteristic.

## The finding in one paragraph

In `DecompressedLocations::CreateDecompressedLocations` (link-time
`0x7ffa15917b34` in the x86_64 slice), the allocation size is
computed as `arg2 * (arg3 >> 29 & ~7) + arg2 * 8 + 24`. The PoC's
`dataWindow` `box2i` contains `yMin = 0x89ffd8ff` (signed int32 =
−1,979,721,473), making the derived height 1,979,721,474 pixels at
512 px width. The `jo` / `jb` overflow guards after the `mul`/`add`
handle full `size_t` overflow, but no earlier bound exists on the
file-supplied image extents. Reproduces in `CGImageSource` and
`NSBitmapImageRep initWithData:`. Full write-up in
[analysis/exr-datawindow.md](analysis/exr-datawindow.md); disassembly
excerpt in [analysis/exr-disassembly.txt](analysis/exr-disassembly.txt).

## Measurement environment

- macOS 26.5 Tahoe, build 25F71
- Mac15,12 with Apple M3, 16 GiB RAM
- Measurement tool compiled `-arch arm64`; `sysctl.proc_translated = 0`
  confirms native arm64 execution at runtime

## iOS

A signed test app on an iPhone 15 Plus running iOS 26.5 reproduces
the virtual reservation (~1.85 GiB of virtual growth, comparable to
macOS),
but iOS does not commit the pages in this code path — resident growth
is only +720 KiB. iOS is **not** characterised here as affected as a
user-visible DoS. The log is in `evidence/ios/` for completeness.

## Disclosure

- Reported to Apple Product Security.
- Apple closed the report without classifying the behaviour as an
  exploitable vulnerability.
- Published here to document the finding. The PoC is a 384-byte
  OpenEXR file whose header carries out-of-range `dataWindow` values.
  It contains no executable code and no payload.
